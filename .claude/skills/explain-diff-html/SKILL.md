# Explain Diff

指定されたコード変更について、リッチでインタラクティブな解説を作成すること。

以下のセクションを含めること。

- **背景 (Background)**: この変更に関係する既存システムを説明する。(そのために周辺コードを広く探索すること。) 読者がどこまで知っているかは分からないので、初学者向けの深い背景説明 (既に知っている読者は読み飛ばせる旨を明記) と、変更に直接関係するより絞った背景説明の両方を含める。
- **直観 (Intuition)**: このコード変更の核となる直観を説明する。ここでの主眼は本質の説明であって、詳細を網羅することではない。おもちゃのデータを使った具体例を用いる。図やダイアグラムを惜しみなく使う。
- **コード (Code)**: コードの変更点を高いレベルから順に解説する。変更を理解しやすいようにグループ化・順序付けする。
- **クイズ (Quiz)**: この PR の理解度を試す問題を出題する。読者が本当に理解できたかを自分で確認できるようにするのが目的である。難易度は中程度とし、PR の中身を実際に理解していないと答えられない程度に難しく、しかしひっかけ問題にはしない。問う中身によって形式を分け、仕様の問題を先、技術の問題を後に並べる。
  - **仕様の問題は選択式**: この PR で何がどう変わるか (挙動・入出力・適用範囲・エッジケースでの振る舞い) を問う。仕様は理解していれば足りるので、インタラクティブな多肢選択式で提示し、クリックすると正誤とフィードバックを表示する。選択肢の見た目から正解を推測できないようにすること: 正解の位置は問題ごとにばらけさせ (常に同じ位置や2番目にしない)、全選択肢の長さ・詳しさを揃える (正解だけが最も長い、という状態は厳禁)。
  - **技術の問題は記述式**: なぜその実装にしたか・どういう仕組みで動くか (設計判断とトレードオフ、使われた技術の原理、素朴に書くとハマる落とし穴とその回避) を問う。技術面は自分の言葉で説明できなければ意味がないので、選択肢は出さずテキスト欄に回答を書かせる。回答を入力すると「模範解答を見る」が押せるようになり、模範解答と採点観点 (回答に含まれているべき要点 2〜4 個のチェックリスト) を表示して読者が自己採点できるようにする。採点観点は「〜に触れているか」と判定できる粒度で具体的に書く。
  - **問題数は PR のサイズに応じて決める**。下表を目安とし、行数より論点 (独立して理解すべき変更のまとまり) の数を優先する。生成物・lockfile・機械的な置換は規模に数えない。技術的な判断を含まない PR (文言修正・設定値の変更のみ等) は技術の問題を 0 問にしてよい。数合わせのための水増しはしない。

    | PR の規模 | 仕様 (選択式) | 技術 (記述式) |
    | --- | --- | --- |
    | 小 (差分〜100 行 / 論点 1〜2) | 1〜2 問 | 1 問 |
    | 中 (〜500 行 / 論点 3〜5) | 2〜3 問 | 2 問 |
    | 大 (500 行超 / 論点 6 以上) | 3〜4 問 | 3〜4 問 |
- **用語集 (Glossary)**: 解説中に登場する技術用語のうち、読者が知らない可能性のあるものを簡潔な定義とともに一覧にする。

フォーマット:

- CSS と JavaScript を含む自己完結した単一の HTML ファイルとして出力する。定型部分 (ベースの CSS・目次生成・選択式の正誤判定と記述式の模範解答表示の JS) は毎回書き起こさず、このスキルの `assets/template.html` をベースにして本文だけを埋めること。全体をセクション見出しと目次を持つ1枚の長いページにする。トップレベルの構造にタブを使わない。スマートフォンでも見られる程度の基本的なレスポンシブスタイルがあると良い。ファイルはコードリポジトリの外のグローバルな場所に置き、ファイル名は必ず今日の日付を `YYYY-MM-DD-` 形式で先頭に付けること (時系列で並び、バージョン管理にも入らないため)。例: /tmp/2026-01-12-explanation-<slug>.html
- Martin Kleppmann のような明晰さと流れのある文章で、classic style で読み手を引き込むように書くこと。セクション間の遷移は滑らかにする。
- 図についてのヒント: 理想的には、少数の図の「ファミリー」を選び、解説全体を通して様々なケースの説明に再利用すること。有用な図の種類の例:
  - UI の変更を説明するための、アプリでユーザーが目にする UI をごく簡略化したもの。
  - コンポーネント間のデータフローや通信を示すシステム図。ここには必ず例となるデータを含めること！
- ASCII アートの図は使わない。図は常にシンプルな HTML デザインで描き、ものの列挙には HTML のリストを使う、といったようにする。
  - コードブロックには常に `<pre>` タグを使う。代わりに独自スタイルの div を使う場合は、その CSS に **必ず** `white-space: pre-wrap` を含めること。さもないとブラウザが改行をすべて1行に潰してしまう。ファイルを保存する前に、HTML ソース内の各コードブロックを確認し、その CSS に `white-space: pre` または `pre-wrap` が含まれていることを確かめること。
- 重要な概念や定義、重要なエッジケースなどにはコールアウトを使うこと。
