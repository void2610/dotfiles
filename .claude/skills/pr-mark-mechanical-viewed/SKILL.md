# pr-mark-mechanical-viewed

**目的: レビュアーの判断が要る箇所以外の変更ファイルをすべて Viewed にし、残ったファイルだけ読めばレビューが済む状態にする。** 機械的な変更の処理は、その中の 1 ステップにすぎない。機械的でなくても、判断が別のファイルで済むなら Viewed にする。

**判定は Claude が差分を読んで行う**。ユーザーに規則や対象を聞かない。PR 番号だけで最後まで進める。

スクリプトは絶対パスで呼ぶ: `~/.claude/skills/pr-mark-mechanical-viewed/scripts/<name>`。作業ファイルはセッションの scratchpad に置く。

## 判定の基準

ファイルごとに「**このファイルの差分を読んで、レビュアーが新たに下す判断があるか**」を問う。無ければ Viewed、あれば残す。

判断が要らない (Viewed にする):

- **機械的な変更**: 識別子・フィールド・型の改名、同じ意味の包み替え (`x.pos` → `x.position.to<T>()`、`dict(js)` → `js.positions_map()`)、同値な式への置き換え、include / import / using の追加、整形、docs・コメント内の名前の追従
- **別のファイルで決まった変更への追従**: 契約 (シグネチャ・基底クラス・ABI) を変えたファイルが残っているなら、その契約に合わせただけの実装・呼び出し側・mock・宣言は Viewed にする。例: 基底の戻り値型が変わり、各 driver が戻り値を新しい型で包むだけの変更。`.hpp` の宣言が `.cpp` の定義を写しているだけの変更
- **生成物**: pygen の生成コード・スタブ等。生成元 (ヘッダ・生成ツール) を残していれば、生成物から新たに判断することはない
- **テストの追従**: 期待値を変えずに、新しい API の呼び方や型に合わせただけのテスト

判断が要る (残す):

- **判断の所在**: 新しい型・API の定義、契約そのものを変えたファイル (公開ヘッダ・基底クラス・ABI ヘッダ)。追従側をすべて Viewed にするかわりに、ここは必ず残す
- **挙動の変化**: 既定値、キーが欠けたときの扱い、反復順、エラー・例外の扱い、時刻・単位の付け方、並行性。書き換えの途中で意味が変わった箇所 (例: `m[k]` の暗黙 0 挿入 → `get(k, fallback)`) も含む
- **このファイルでしか見えない設計判断**: 可視性・カプセル化の変更、責務の移動、新しいヘルパの導入方針
- **テストの意味の変化**: 期待値の変更、テストケースの削除・統合 (網羅が減っていないか)
- **生成ツール・ビルド設定の手書きロジック**
- ファイルの一部の hunk だけでも判断が要るなら、ファイルごと残す。迷ったら残す

## 手順

1. **対象の解決**: 引数から `owner/repo` と PR 番号を決める。番号だけなら `gh repo view --json nameWithOwner` で cwd のリポジトリ。
2. **取得と分割**: `gh pr diff <N> -R <repo> > diff.patch` → `python3 -I scripts/split_diff.py diff.patch split` (ファイルごとの patch と `index.tsv`)。
3. **未チェックだけに絞る**: `scripts/viewed_state.sh <repo> <N> > state.tsv` で UNVIEWED のパスだけを対象にする (ユーザーが既に付けたものは読まない・触らない)。
4. **判断の所在を特定する**: PR 本文とコミット見出しから PR の意図を掴み、判断が集まるファイル (新しい型・API の定義、契約の変更、ABI) を先に決める。以降の「追従」の判定はこれを基準にする。
5. **全ファイルを読んで判定**: 各 patch の `-` / `+` 行を読み、[判定の基準](#判定の基準) で分ける。
   - 1 段目: 機械的な変更だけのファイルを除く
   - 2 段目: 残りのうち、手順 4 で決めたファイルへの追従・生成物・テストの追従を除く。追従と見なす前に、そのファイルで挙動が変わっていないかを確かめる
   - 残すファイルには「何を判断するか」を 1 行で書いておく (報告に使う)
   - ファイルが多いときは patch を数十本ずつ読む (`grep -E '^(\+\+\+|[-+][^-+]|[-+]$)' split/files/<n>.patch`)。zsh では未クォートの変数が分割されないので、ループは `bash -c` で回す。数百本規模なら Agent に塊ごとに判定させ、残すと返したものの理由を自分で確かめる
6. **チェック**: Viewed にするパスを 1 行 1 パスで書き、`scripts/mark_viewed.sh <repo> <N> <list>`。
7. **検証**: `scripts/viewed_state.sh <repo> <N>` で UNVIEWED に残ったものを列挙し、手順 5 の判定と一致するか確かめる。

## 報告

- 今回付けた本数 (機械的 / 追従・生成物 の内訳) と、以前から VIEWED だった本数
- 残したファイルを**読む順**に並べ、各ファイルに「何を判断するか」を 1 行で書く。判断の所在 (定義・契約) を先、挙動の変化を次、テストを最後に置く。具体的な hunk があれば `path:line` で示す
- 読まずに残したファイルがあればそう書く

## 禁止

- 判定の規則や対象をユーザーに聞く・作らせる
- UNVIEWED に戻す操作 (`unmarkFileAsViewed`)。ユーザーが付けた Viewed を消す
- レビューコメント・approve など Viewed 以外の書き込み
