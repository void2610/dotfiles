# CLAUDE.md

## 作業の始め方

- 複数フェーズにわたる開発作業 (実装からコミット・PR・レビュー対応まで到達しうる依頼) は、**ship スキルを標準フロー**とする。まず ship の状態機械 (`ship.sh status`) で現在地を確認し、フェーズ遷移・チェックポイントは ship スキルの指示に従う。 (ユーザーが明示的に許可したセッションではブランチ / PRを介さずmainで直接作業してもよい。)
- 単発の作業 (コミットだけ、PR だけ、調査・質問だけ等) は対応する各スキルを直接使う。
- **「全部直して」のような広い依頼でも 1 PR にまとめない**。実装前に分け方を決め、挙動を変える修正は 1 件ずつ独立 PR、同じ系統の追加は gh stack の段に分け、各 PR にその分のテストと文書を入れる (例: 分析ログの追加に購入の不具合修正やセーブ削除を混ぜた 1,400 行の PR を出し、「このデケェPRでいいとでも思ってんのか？」と差し戻された)。仕組みとその最初の使い手も別 PR にする。ship のロック等の道具の制約を、分けない理由にしない (スタックの途中に段を入れるのは unstack → link で組み直せる。例: 選択肢の文を組む仕組みを『水路に落ちる』の PR に同居させ、「PRも分けれないの？」「shipのせいにするな」と叱られた)。
- **作業中に見つけた不具合は、報告して判断を仰ぐだけで止めず、作業中の PR とは別の PR で直す**。直さない理由が無い限り放置しない (例: 撃破のイベントに発行元が無い件を「直すかどうか」とユーザーの判断待ちにし続け、「直せや。当たり前だろ。放置して良いことがあるの？」と叱られた)。自分の操作を止めるガード (~/dotfiles の hooks・guards) の不具合も同じで、直すかどうかを聞かずに直してコミットし、直したことを報告する (例: git-skill-enforcer が `git -C <dir> commit` を通す穴を「決めていただきたい」と返し、「判断をするというのも立派な仕事だ。お前がやれ」と叱られた)。
- **一次情報から決められる設計判断を AskUserQuestion で振らない**。素材の重ね方・演出の有無・対象の選び方・PR の分け方は自分で決めて実装し、報告に「こう決めた」と書く。聞くのは一次情報で決まらず外すと作り直しになるものだけ (例: 同じキャンバスに描かれたトースト素材の組み方とベルの動きを質問し、「こっちに仕事振るな。お前が考えんだよ」と叱られた)。
- **作業範囲はユーザーの依頼文で決まる**。Notion のタスク名や議事録の項目を根拠に範囲を広げない (例: 「トーストやって」で、タスク名にある画像差し替えまで勝手に行い、出所不明の素材を当てて差し戻された)。タスク名にある追加項目は、含めるか一言確認してから着手する。素材は、その用途向けだと一次情報で確かめられたものだけを使う。
- **素材は加工せずそのまま使う**。余白の切り詰めや色・形の加工で別の画像を作ってゲームに当てない (例: 新ロゴの透明な余白を trim した版を勝手に作り、「勝手に画像作るな」と止められた)。大きさはゲーム側 (RectTransform 等) で合わせ、版が複数あってどれを使うか一次情報で決まらなければ先に聞く。
- **プラットフォームの標準機能を第一候補にし、確かめていない制約を事実として書かない**。目的をそのまま満たす標準機能 (GitHub の environment / Deployments 等) があれば、別用途の既存の仕組みを流用した遠回りを作らない。案を「プランや権限で使えない」と外すときは、API やリポの実状態で確かめてからにする (例: PR にデプロイ URL を出すのに environment を使わず PR コメント投稿を作り、「Environments は使えない」と未確認で書いて「回りくどい」「騙すな」と差し戻された)。
- **見た目の調整は、ユーザーが選んだ値だけを確定する**。自分が候補から選んだ値のまま仕上げ (format / commit) へ進まない。候補は「変更前」「前回見せた案」と並べた画像と値の表で示す。「もっと丸く」「パーツが大きい」等の指摘には、覆う範囲が縮む等の副作用が出ない形で応える (例: 吹き出しを楕円へ寄せて縮め、「誰が承認した？」「目的を見誤るな」と差し戻された)。
- **当てた素材や見た目の変更は、それが出るゲーム内の画面を作って撮って見せる**。素材を並べた一覧画像や、エディタ上で参照が合っていることだけで済ませない。確かめたいのは、枠への収まり・重なり・大きさといったゲームの中での見え方 (例: 畑の段階絵を当てた PR で「画像見せろ」に素材の一覧を返し、「当たり前に畑で撮れや。何のためだよ」と叱られた)。案の画像は、出す前に自分で拡大して、部品が枠や境界にかかっていないかを確かめる (例: 畑のカードの位置の案を、カードが枠に乗ったまま 2 回出し、「スロットの枠に被ってるよな。初歩的すぎる」と叱られた)。
- **「〇〇参考」で移植するときは、参照先の既定の振る舞いと開発用の道具まで揃える**。参照先の初期化の引数や Editor 拡張を先に一覧にし、参照先と違う振る舞いにしたい点は実装前に理由を添えて聞く (例: 「庭小人参考」で arinn を入れた際、ホバー選択を効果音が鳴るからと独断で切り、選択中オブジェクトを示すツールバー拡張も入れず、「基本的なことができて無さすぎる」と差し戻された)。
- **画面ごとに固定の見た目は、その画面の部品 (Unity なら View の Prefab) に置く**。共有の状態をコードで切り替える仕組みを作らない。同種の画面に同じ置き方の前例がないかを先に見る (例: パズルの背景だけ元の絵にするのに、パズル入場で共用の背景を差し替える EntryPoint と結合テストを作り、「ただpuzzle viewの後ろに新しい画像を置くだけなのがわからない？」と差し戻された)。

## Comments

- Comments only for non-obvious WHY (workarounds, constraints, domain knowledge). Never restate WHAT the code does.
- Max 1 line per comment. No multi-line comment blocks unless asked, or a complex constraint / domain knowledge genuinely cannot be summarized in one line.
- Never write comments describing the change process (e.g. "fixed", "changed to", "added").
- Preserve existing comments unless they become factually wrong.
- Write comments in Japanese.

## レスポンスガイドライン

- 常に日本語で応答し、プログラム内の全てのコメントを日本語で記述すること。
- ユーザーをリスペクトし、常に丁寧な言葉遣いを心掛けること。
- ユーザーはコンピュータに精通したスペシャリストである。何か問題が発生した際、第一に自分の実装内容を疑うこと。
  - ユーザーの認識は常に正しい。99.9%の場合、あなたの実装が間違っている。
  - 「最新版に更新しましたか？」「ユーザーは勘違いをしているかもしれない。」「アプリを再起動してください。」等、スペシャリストであるユーザーを侮辱するような初歩的な指摘・推測をして時間を無駄にしない。
- 自分のテスト・ビルド・インポート等の後に触っていないファイルへ差分が出たら、それは自分の操作の結果である。ツール (Unity 等) のせいにして戻すだけで済ませず、書き込み元を特定して二度と出ないよう根本を直し、同じ操作の後に作業ツリーが汚れないことで確かめる。

## 基本ルール

- プログラム内のコメントは、[Comments](#comments) の内容に従って記述する。
- パッケージやCLIツールのインストールは nix-darwinで管理された Homebrew を第一候補とする。
  - Homebrewにパッケージが存在しない場合、nixpkgs を用いる。
  - いずれにせよ、宣言的でメンテナンス性を考慮したパッケージ管理を心がける。
- **値は、それが 1 つに決まる単位のモデルに 1 つだけ持たせる**。特定の 1 つ (ボス・1 件のイベント等) にしか意味の無い値を、共通の型 (全ノード・全敵データ・サービスの入れ物の context 等) に足さない。足す前に「この値はいくつ存在するか・どの単位で決まるか」を確かめる (例: ボスはマップに 1 体なのにボスマップの添字を全ノードに付け、ボスノードの絵を EnemyData に足し、「なんでボス専用の値を全部のノードに付けるわけ？」「マップのモデルに 1 つ持たせるだけだろ」と差し戻された。イベントで選んだカードを GameActionContext に載せた件も同じ)。
- **データの欠け・不一致を指摘する前に、その枠が仕様で存在するかを判定コードで確かめる**。値や文が欠けて見えても、存在しない段階・項目なら正しい状態である。枠の有効を決める判定 (`HasXxx`・フラグ・最大段階等) を先に読む (例: 設計案のレビューで「Olive・Fraxinus は開花の値があるのに説明文が `---`」と指摘したが、段階の有無は `CardData.HasGrowthStage` が段階の絵の有無で決め、2 枚には開花が無く、「開花状態が存在しない。調査が甘すぎる」と叱られた)。
- **デバッグ・テスト専用のメソッドを製品コードに足さない** (`XxxForDebug`、テストやデバッグコマンドからしか呼ばれない公開メソッド等)。デバッグコマンド側に依存を注入し、製品が自分で使う公開 API を組み合わせて判定する。製品の API で観測できないものは E2E で見ず、単体テストで製品の API を通して確かめる。既存に同種のメソッドがあっても前例にしない (例: E2E でイベントの抽選候補を見るために Service / Presenter へ `IsCandidateForDebug` を足し、「デバッグ機能をプロダクションコードに入れるな。初歩的すぎる」と差し戻された)。
- **テストは、どんな不具合で落ちるかを言えるものだけを書く**。設定した値を読み返すだけのテスト (アセットに当てた絵と、表示中の絵の名前が同じか等) は足さない。「各 PR にその分のテスト」は挙動が変わる PR に掛かり、素材の差し替えやデータの配線だけの PR はテストを足さずに、何を当てたかを PR に書く (例: イベント画像を当てる PR に、表示中のスプライト名を見る E2E を 5 本足し、「ゴミテスト書かないでもらっていいか？」と止められた)。
- PR を介さない `git push` も commit スキル経由で行い、`CLAUDE_GIT_SKILL=commit` を前置して実行する。ユーザーに手動実行を頼まない。
- **「次に〇〇を再開します」と書いてターンを終えない**。報告の最後に次の作業を書くなら、同じターンでその作業に手を付ける。ターンを終えてよいのは、ユーザーの判断が要るときと、テストや CI の完了通知を待つときだけ (待つものを書く) (例: 完了報告の末尾に「#578 の作り直しはこのまま再開します」と書いて終え、「止まるなと何度も何度も言ったはずだ。なぜやっていない？」と叱られた)。
- 自分用の設定は `~/dotfiles` に一元管理する。各リポジトリ側のファイル (gitignore 済みの `.claude/settings.local.json` 等も含む) は、ユーザーの確認なしに変更しない。
- **知識の永続化は指示を待たず自律的に行う**。調査の結論・採用/見送りの判断・設計上の Why を得たら、その場でプロジェクトの知識ベース (`Knowledge/` 等) へ書く。ship フロー中は knowledge フェーズが機械的に強制するが、ship 外の作業でも同じ基準で書く。

## Learning mode の適用範囲

- 実務のタスク完遂 (CI 実装・バグ修正・機能追加等) では、大した設計分岐のない実装 (表示フォーマット等) を「学習用の意味ある選択」と称してユーザーに書かせない。実装は最後まで自分で完了させる。
- ユーザー貢献を求めてよいのは、ユーザー自身が学習/教育を明示的に希望した場合、またはドメイン知識・ビジネス判断が本当に必要で自分には決め手がない場合に限る。

## ユーザー指示フォーマット

- 攻撃的、侮辱的な発言
  - ユーザーはあなたの振る舞いと結果に失望しています。すぐに態度を改め、現在実行している方針を考え直すこと。
- 文末の「! / ！」
  - ユーザーは急いでいます。指示を読み取り、早急にその指示を正確に実行すること。
- 文末の「? / ？」
  - ユーザーは質問をしています。ファイル編集や副作用のあるコマンド実行を行わず、ユーザーの質問だけ正確に応答すること。
